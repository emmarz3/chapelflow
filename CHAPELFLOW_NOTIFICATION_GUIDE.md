# Phase 4 notification centre

Users can open **Notifications** and **Notification settings** from the portal navigation. The bell uses a server-side unread count; the inbox loads additional pages, marks items read, and opens the linked screen.

Settings are stored per user at `GET/PATCH /api/v1/communications/preferences/me/`. The master switch, delivery channels, and each topic are independent. Public prayer notices require a separate opt-in. Quiet hours delay external delivery in the user's IANA time zone; in-app items remain available when the user signs in. Existing preferences are linked to their users by the Phase 4 data migration.

All new notifications use `apps.notifications.preferences.queue_notification`. It checks active-account status, the master switch, topic, channel, and quiet hours before creation. `deliver_notification` checks again immediately before delivery, so a later opt-out also blocks queued messages. Announcement dispatch rechecks branch/group membership and preferences. Live-service notices go only to active users in the publishing branch. Unique idempotency keys prevent repeated fan-out, while locked delivery state prevents overlapping workers from sending the same row. The periodic `dispatch_due_notifications` task recovers due quiet-hour notifications and pending rows that were never queued; Celery retries recorded provider failures.

Email uses Django's configured email backend. SMS uses the configured Termii provider when credentials are present; otherwise its status is `STUBBED`, never `SENT`. Browser push is unavailable because this application has no device subscription and permission lifecycle. The settings page explains this and does not request browser permission. New push notifications and push announcement campaigns are rejected; legacy push rows remain stubbed without contacting FCM. Do not enable push until subscription storage, permission/revocation handling, credential protection, and browser tests are implemented.

Provider responses, attempts, and `FAILED`/`STUBBED` states are stored on notifications. A failed delivery can be retried through the existing Celery task using its notification ID; current preferences are checked again and sent/delivered rows are skipped. If a worker stops while a row is `SENDING`, reconcile the external provider before resetting it: a send may have succeeded without a recorded response. This avoids blind duplicate external delivery.

Validation run: 78 affected Django tests and 132 frontend tests passed; Django system check, migration drift check, and `npm run build` passed. The Phase 4 tests cover opt-outs, opt-ins, recipient targeting, duplicate prevention, read counts, quiet hours, provider failure/retry, public-prayer consent, live service targeting, and unsupported push. A wider legacy Django run exposed unrelated failures in old pastoral, visitor, group, and volunteer tests; those remain separate regression work.
